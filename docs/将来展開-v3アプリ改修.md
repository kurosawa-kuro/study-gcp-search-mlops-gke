## 2. PostgreSQL テーブル

## 5. データフロー (Phase 3 = Local)

0. **Redis SYN-2** (`SearchCachePort`) で `(query, filters, top_k, explain)` キーで cache lookup。HIT なら 1〜6 を skip して即返却 (TTL 60s 以内の同条件再検索)
1. **Redis SYN-1** (`SynonymExpanderPort`) で query を同義語展開 (例: `マンション` → `マンション アパート 共同住宅`)。**lexical 側のみ** に流す (semantic side は素のクエリのまま、ME5 の意味類似に任せる)
2. **Meilisearch** で展開クエリを BM25 + filter にかけ候補を取る (lexical) → `LexicalResult[]`
3. **multilingual-e5** で **元クエリの** 意味類似度を計算 (semantic encoder + pgvector ANN) → `SemanticResult[]`
4. **RRF** (`rrf_fuse`) で異種 score の順位を統合し top-K に絞る
5. **PostgreSQL** から `properties` + `feature_mart_property_features_daily` で候補の特徴量を補完
6. **LightGBM LambdaRank** (`Booster.predict`) で最終順位を決める
7. **PostgreSQL** `ranking_log` に full pool を永続化、`/search` レスポンス返却
8. **Redis SYN-2** に応答を `search:v1:<sha256>` で SETEX (TTL=60s)。次の同条件は HIT で短絡

> **Redis の 2 役割は別 prefix で完全分離**: `syn:<token>` (SYN-1 同義語辞書、ranking 精度) と `search:v1:<hash>` (SYN-2 レスポンスキャッシュ、UX/latency)。同じ Docker container を共有するが衝突しない。

オンライン経路の詳細シーケンス図は [Phase 7 docs/01 §2.2.2](../../../7/study-hybrid-search-gke/docs/architecture/01_仕様と設計.md) を参照 (Phase 3 でも論理は同じ、adapter 実装が違うのみ)。

## Phase 4 に入れるべきデータパイプライン

Phase 4 の主役は、単なる Cloud Run 化ではなく、**検索アプリを改善し続けるための学習データ基盤**です。

```text
Cloud Run Search API
  ↓
structured event log
  ↓
GCS raw event logs
  ↓
BigQuery raw_events
  ↓
BigQuery labeling SQL / Cloud Run Job
  ↓
ranking_labels
  ↓
LightGBM LambdaRank training dataset
  ↓
Cloud Run Job retrain
  ↓
GCS model artifact
  ↓
BigQuery evaluation_metrics
```

Cloud Run のログは Cloud Logging に送られ、JSON 形式の構造化ログは `jsonPayload` として扱えるため、検索ログ・クリックログ・資料請求ログをイベントとして扱いやすいです。Cloud Logging の sink は Cloud Storage、BigQuery、Pub/Sub などにルーティングでき、BigQuery は Cloud Storage から batch load も可能なので、Phase 4 の教材としては **GCS raw → BigQuery curated** の流れを明示するのがよいです。([Google Cloud Documentation][1])

運用上は Cloud Logging sink から BigQuery へ直接流す構成も可能ですが、教材では **GCS を raw data lake、BigQuery を分析・ラベル作成・学習データ整備の場所**として分けた方が学習価値が高いです。Cloud Logging の BigQuery routing は小さな batch として BigQuery に流せるため、Phase 4 の optional / advanced 経路として扱えます。([Google Cloud Documentation][2])

## Redis を「使ったことにする」問題への対策

ご提示メモにある通り、Redis を入れると決めたのに実装で使われないのは破綻ポイントです。
Phase 3 では Redis を必須にして、以下のどれかではなく **全部**を最低限テスト対象にするのがよいです。

```text
1. query embedding cache
2. normalized query + filters の検索結果 cache
3. rerank feature cache
```

受け入れ条件はこうします。

```text
- Redis cache miss 時に embedding adapter が呼ばれる
- Redis cache hit 時に embedding adapter が呼ばれない
- 同一 query + filters の検索で cache key が一致する
- TTL が設定されている
- pytest で RedisAdapter の呼び出しが検証される
```

Phase 4 で Redis を cloud 化する場合は Memorystore for Redis が自然ですが、Cloud Run から接続するには Redis instance の authorized VPC network へのアクセス設計が必要です。教材の過剰化を避けるなら、Phase 4 の必須範囲は **CachePort 維持 + optional Memorystore** とし、Phase 7 で GKE / VPC 前提の本格運用に寄せるのがよいです。Memorystore for Redis は Google Cloud の fully managed Redis service で、Cloud Run から接続するには VPC network access が必要です。([Google Cloud Documentation][3])

## Phase 7 の完成形

Phase 7 は、Phase 4 のログパイプラインを本番 MLOps に拡張します。

```text
GKE Search API / KServe Reranker
  ↓
event logs
  ↓
BigQuery
  ↓
Cloud Composer DAG
  ↓
labeling
  ↓
feature generation
  ↓
Vertex AI Feature Store
  ↓
Vertex Vector Search index update
  ↓
Vertex AI Pipelines training
  ↓
Vertex Model Registry
  ↓
evaluation gate
  ↓
KServe deployment
```

Vertex AI Pipelines は container と Google Cloud service に基づく ML workflow を serverless に orchestration するサービスで、Vertex Model Registry は ML model lifecycle を管理する central repository です。Feature Store は BigQuery data source を使って feature serving でき、Vertex Vector Search は検索・推薦向けの fully managed vector search 基盤として扱えます。([Google Cloud Documentation][6])

Cloud Composer / Managed Service for Apache Airflow は DAG を管理して workflow を schedule / monitor するための層として Phase 7 に置き、GKE は containerized application を大規模に deploy / operate する基盤、KServe は Kubernetes 上の AI model serving platform として位置づけます。([Google Cloud Documentation][7])

EDAから始める。不動産データもできるだけすべてフェーズでに通わせる

## 理由

住宅価格予測では、正解データは比較的シンプルです。

```text
物件特徴量 → 価格予測 → 実際の価格と比較
```

一方、検索では正解データが直接存在しません。

```text
検索クエリ
→ 検索結果表示
→ クリック
→ 詳細閲覧
→ 資料請求
→ 問い合わせ
→ 成約
```

この一連の行動ログから、あとで「この検索結果は良かったのか？」を推定する必要があります。

そのため、検索 MLOps では以下が重要になります。

```text
検索アプリ
→ 行動ログ収集
→ ログ蓄積
→ 正解ラベル作成
→ 評価データ作成
→ リランキング再学習
→ 検索品質評価
→ 再デプロイ
```

これは **GCP MLOps の土台である Phase 4 のテーマとかなり相性が良い**です。

Phase 4 はすでに以下を扱います。

* Cloud Run
* BigQuery
* GCS
* Secret Manager
* Terraform
* WIF
* Cloud Logging

ここに検索ログパイプラインを足すと、単なる「GCP に載せました」ではなく、**検索システムを改善し続ける MLOps** になります。

## 「クリック」「資料請求ボタンクリック」は正解データか？

結論、**そのままでは正解データではなく、弱い教師信号です。**

かなり重要です。

```text
検索結果表示 = impression
物件クリック = weak positive
詳細ページ滞在 = stronger positive
お気に入り = stronger positive
資料請求ボタンクリック = strong positive
問い合わせ完了 = very strong positive
成約 = strongest positive
即離脱 = weak negative
表示されたが無反応 = weak / noisy negative
```

なので、こう定義するのがよいです。

| 行動           | 正解データとしての強さ | 扱い                   |
| ------------ | ----------: | -------------------- |
| 検索結果に表示      |          なし | impression           |
| 物件クリック       |        弱い正例 | weak positive        |
| 詳細ページ閲覧      |      中程度の正例 | positive             |
| 長時間滞在        |      中程度の正例 | positive             |
| お気に入り        |        強い正例 | strong positive      |
| 資料請求ボタンクリック  |        強い正例 | strong positive      |
| 資料請求完了       |     かなり強い正例 | very strong positive |
| 問い合わせ完了      |     かなり強い正例 | very strong positive |
| 成約           |       最強の正例 | final conversion     |
| 表示されたがクリックなし |        弱い負例 | weak negative        |
| クリック後すぐ離脱    |        弱い負例 | weak negative        |

つまり、資料請求ボタンクリックはかなり有力ですが、厳密にはこうです。

```text
資料請求ボタンクリック = 強い正例候補
資料請求完了 = より強い正例
成約 = 最終正解に近い
```

検索ランキング用には、いきなり成約だけを見るとデータが少なすぎます。
そのため、現実的には以下のような重み付きラベルにします。

```text
click: 1
detail_view: 2
favorite: 3
request_button_click: 4
request_complete: 5
contract: 10
```

LightGBM LambdaRank 用なら、クエリ単位で relevance label を作る形です。

```text
query_id, property_id, relevance_score
```

例：

```text
札幌 1LDK 駅近, property_001, 5
札幌 1LDK 駅近, property_002, 2
札幌 1LDK 駅近, property_003, 0
```

## 破綻条件

この設計が破綻するのは、主に以下です。

### 1. Phase 3 に詰め込みすぎる

Phase 3 で GCS / BigQuery / Dataflow / Composer まで入れると破綻します。

Phase 3 はあくまでローカルです。

```text
PostgreSQL にログ保存
簡易 labeling
LightGBM reranker 再学習
```

ここまでで止めるべきです。

---

### 2. クリックを「完全な正解」として扱う

これは危険です。

クリックは以下の影響を受けます。

* 表示順位
* 写真の見栄え
* タイトル
* 価格の安さ
* 釣り物件
* ユーザーの偶然
* UI の配置

そのため、クリックは **正解そのものではなく、弱い正解シグナル** として扱うべきです。

---

### 3. 成約だけを正解にする

これも危険です。

成約は最も強い正解に近いですが、データ量が少なすぎます。
学習データとしてはスパースになりやすいです。

したがって、現実的には以下の複合ラベルがよいです。

```text
クリック
詳細閲覧
お気に入り
資料請求クリック
資料請求完了
問い合わせ
成約
```

これらを重み付けして、ランキング学習用の relevance label に変換します。
