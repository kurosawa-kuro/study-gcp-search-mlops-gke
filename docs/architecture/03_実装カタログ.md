### 7.4 頻発 incident memo

#### 2026-05-09/10 sprint で固定化された 4 incident (まとめ)

| incident | 詳細 | 永続化先 |
|---|---|---|
| WIF pool soft-delete 30 日残置 → tf-apply 409 | `--from-step tf-apply` 単独実行で step 3 (`recover-wif`) を skip すると WIF 409 で 30+ 分の出戻り | `scripts/setup/tf_apply.py` 冒頭で `recover_wif_main()` idempotent hook + contract test `test_tf_apply_invokes_recover_wif_as_pre_step` |
| destroy-all step 分離なし (deploy-all との非対称) | step 単位リカバリーが destroy 側で効かず、PDCA loop 再現性が片肺 | `scripts/setup/destroy_all.py` を 8 step + `DestroyStep` dataclass + `--from-step/--to-step` slicing で対称化。contract test `test_destroy_all_provides_step_slicing_symmetric_with_deploy_all` |
| terraform_lock parser が ANSI escape で fail | bg kill 後の lock 残置で自動 unlock が機能せず手動 force-unlock が必要に | `scripts/infra/terraform_lock.py` を ANSI escape strip + 緩い行頭 anchor (`^[^A-Za-z0-9]*ID:`) に修正。test に実 ANSI escape 入りケース追加 |
| sync-elasticsearch が ECK ApplyingChanges race | step 10 が ES 起動完了より早く走ると `Server disconnected` で fail | `scripts/infra/elasticsearch_wait.py` 新設、`_run_sync_elasticsearch` 冒頭で `wait_until_es_healthy()` (green/yellow まで poll、5 min timeout)。Makefile target も `--project-id` / `--es-url` を forward。両方 contract test pin。framework 化: `DeployStep.precondition` field + main loop が wait を呼出 (deploy_all + destroy_all 対称、unit test 3 件) |
| **ECK reconcile stall (真の root cause、2026-05-10 確定)** | 2 回連続再発 → log 調査で 2 つの構造的 bug を特定: (1) NetworkPolicy 漏れ (elastic-system ns ingress 不在 → ECK Operator が ES `:9200` に到達不可)、(2) canonical URL `http://...` と ECK 8.x default `xpack.security.http.ssl.enabled=true` の不整合 → `Server disconnected` | (1) `infra/manifests/elasticsearch/networkpolicy.yaml` に `elastic-system` ns ingress 追加。(2) `infra/manifests/elasticsearch/elasticsearch.yaml` に `spec.http.tls.selfSignedCertificate.disabled: true` + `xpack.security.authc.anonymous.{username,roles,authz_exception}` 追加 (HTTP + anonymous superuser、学習プロジェクト前提)。production 化 (HTTPS + password auth) は別 sprint backlog |

#### search-api ダミーイメージ混入
- 症状: `search-api` が `gcr.io/cloudrun/hello` で起動し、`ops-search` / `ops-search-components` が誤検知または失敗
- 直接原因: `infra/manifests/search-api/deployment.yaml` のダミー `image` が想定外の apply 手順で再適用される
- 恒久回避:
  - `infra/manifests/search-api/deployment.yaml` の `image: gcr.io/cloudrun/hello` に「placeholder / 本番適用禁止」コメントを維持
  - `scripts/deploy/api_gke.py` / `make deploy-api` を canonical 手順として固定
  - 適用後 `kubectl -n search get deploy/search-api -o jsonpath='{.spec.template.spec.containers[0].image}'` を必ず確認
  - スモーク前チェックに image 検証を追加し、`gcr.io/cloudrun/hello` の場合は即 fail-fast
