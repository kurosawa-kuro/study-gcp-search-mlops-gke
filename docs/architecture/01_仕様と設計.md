## Phase 設計の軸 (改訂版)

- Phase 1: **ML 基礎に集中** (学習・評価・保存) — **コード化対象**
- Phase 2: **App / Pipeline / Port-Adapter** を導入 — **コード化対象**
- Phase 3: 不動産ハイブリッド検索の **Local 完成形 + 最小行動ログ収集** — **コード化対象** (PostgreSQL `search_events` / `search_impressions` / `user_actions` + 弱教師 ranking label + LightGBM 再学習用 training dataset)
- Phase 4: **GCP MLOps の土台 + 検索ログ正解データパイプライン** (Phase 3 からの足し算で構築、Vertex AI 以降は含めない) — **コード化対象** (Cloud Run 構造化ログ → GCS raw → BigQuery curated / `ranking_labels` / `training_dataset` / `evaluation_metrics` (NDCG@10 / Recall@K / CTR / CVR) → GCS model artifact)
- Phase 5: **Vertex AI MLOps 化の技術境界** — **論理 Phase (個別コード保守なし、Phase 7 完成版を参照)**
- Phase 6: **PMLE 追加技術 + Composer 本線化の論理境界** — **論理 Phase (個別コード保守なし、Phase 7 完成版を参照)**
- Phase 7: **教材コード完成版 / canonical 起点 / 到達ゴール / 継続改善 MLOps サイクル** — **コード化対象** (Phase 4 の検索ログ正解データパイプラインを Composer / Vertex Pipelines / Feature Store / Vector Search / Model Registry / GKE / KServe に接続し、ログ収集 → ラベル作成 → 特徴量更新 → ベクトル index 更新 → reranker 再学習 → 評価 → deployment gate → KServe 反映 までを継続改善サイクルとして本 phase 配下に集約)

## 設計思想の不変性

- Phase 間のコードは原則共有しない (教材としての独立性を優先)
- ただし **設計思想 (Port/Adapter / 依存方向 / `core → ports ← adapters`) は一貫** させ、**adapter 実装だけ差し替える**
- 実行方式の段差 (Docker Compose → uv + クラウド → Vertex AI → GKE) は、同じ設計思想を保ったまま実行基盤だけを段階的に差し替える学習設計

## Cloud Composer の位置づけ — Phase 7 docs §3 が canonical

**Phase 7 で本実装 (canonical 起点)**。教育上は Phase 6 が Composer 本線化の論理境界として位置づけられる (Phase 6 配下に独立コードはない)。Phase 4 までは Cloud Scheduler + Eventarc + Cloud Function の軽量経路で retrain trigger を扱う。詳細 (上下関係 / DAG 段差 / カニバリ NG) は **Phase 7 [`docs/architecture/01_仕様と設計.md` §3](../../7/study-hybrid-search-gke/docs/architecture/01_仕様と設計.md)** が canonical。

### 検索ログ正解データパイプラインの 3 段差 (v3 設計改訂、2026-05-05)

| Phase | 検索ログ・行動ログ | 正解データ・training dataset | 再学習 trigger |
|---|---|---|---|
| **Phase 3 (Local)** | PostgreSQL `search_events` / `search_impressions` / `user_actions` (ローカル最小契約) | 重み付き relevance ローカル labeling job (Python / SQL) → LightGBM training dataset (local CSV/Parquet) | 手動 (`make` ターゲット) |
| **Phase 4 (GCP MLOps 土台 = 軽量経路)** | Cloud Run 構造化ログ → Cloud Logging → GCS raw event logs → BigQuery `raw_events` → BigQuery `curated` | BigQuery labeling SQL → BigQuery `ranking_labels` → BigQuery `training_dataset` → GCS model artifact + BigQuery `evaluation_metrics` (NDCG@10 / Recall@K / CTR / CVR) | Cloud Scheduler + Eventarc + Cloud Function → Cloud Run Job retrain (軽量 orchestration) |
| **Phase 7 (canonical = Composer 本線)** | Phase 4 の経路を継承し、Composer DAG が orchestration の本線を担う | Composer DAG `retrain_orchestration` が labeling SQL → BigQuery `ranking_labels` → BigQuery `training_dataset` → Vertex AI Pipelines retrain → Vertex Model Registry (deployment gate 評価) → KServe 反映 を駆動 | Composer DAG schedule (`daily_feature_refresh` / `retrain_orchestration` / `monitoring_validation` の 3 DAG)。Vertex `PipelineJobSchedule` は完全撤去、Cloud Scheduler / Eventarc / Cloud Function trigger は smoke / manual trigger 用途で残置 |

## 共通非負制約

### 全 Phase 共通

- 教材対象外技術は導入しない (親 [`README.md` §1](../../README.md))
- 設計思想 (Port/Adapter / 依存方向 / `core → ports ← adapters`) を破壊しない
- Phase 間のコード共有や広域リファクタは原則行わない

### Phase 3 / 4 / 7 (ハイブリッド検索系コード化対象)

- ハイブリッド検索中核 5 要素を維持 (詳細は Phase 7 docs/01 §2.3)
- 検索品質改善はこの基本構成を前提に行う
- 置換・削減・無効化は事前の明示合意を必要とする

### Phase 4 (GCP MLOps 土台 + 検索ログ正解データパイプライン = 独立コード)

- **Phase 7 完成版からの引き算ではなく、Phase 3 からの足し算で構築** (v3 設計改訂、2026-05-05)
- 主役は **検索アプリを改善し続けるための学習データ基盤**:
  - **基盤**: Cloud Run / Cloud Run Jobs / BigQuery / GCS / Secret Manager / Cloud Logging / Artifact Registry / Cloud Build / Terraform / WIF / IAM
  - **行動ログパイプライン**: Cloud Run 構造化ログ → Cloud Logging → GCS raw event bucket → BigQuery `raw_events` / `curated` → labeling SQL → BigQuery `ranking_labels` / `training_dataset` → BigQuery `evaluation_metrics` (NDCG@10 / Recall@K / CTR / CVR)
  - **再学習 trigger**: Cloud Scheduler + Eventarc + Cloud Function による軽量 orchestration → Cloud Run Job retrain → GCS model artifact 保存
  - **ベクトル検索**: BigQuery `VECTOR_SEARCH` (GCP マネージドサービス基礎習得の範囲、Vertex Vector Search への置換は Phase 7 で実施)
- **Phase 4 の到達点**: BigQuery 上で NDCG@10 / Recall@K / CTR / CVR を計算でき、再学習候補モデルを GCS に作れること。Vertex Model Registry 登録は Phase 7 側に寄せる
- **Vertex AI Pipelines / Feature Store / Vector Search / Vertex Model Registry / Cloud Composer / Dataflow / GKE / KServe / PMLE 追加技術は扱わない** (Phase 7 完成版に集約、Phase 5 / 6 で分解説明)

### Phase 5 / 6 (論理 Phase = コード保守なし)

- 個別コードを持たない。Phase 7 完成版コードを基準にして技術境界を資料化する
- 各 Phase スライド・ドキュメントでは Phase 7 配下の参照先を必ず明示する

### Phase 7 (到達ゴール = canonical 起点)

- Phase 5 / 6 の技術要素も Phase 7 配下に集約
- Cloud Composer 本線 + Vertex AI Pipelines + Feature Store + Vertex Vector Search + Model Registry + BigQuery + Meilisearch + GKE + KServe + PMLE 4 技術を本 phase で本実装
- ハイブリッド検索中核コードの挙動は絶対に変えない
- default feature flag では Phase 5 相当の挙動を維持 (新技術は opt-in)
- `make check` / parity invariant / Port/Adapter 境界検知 / WIF は追加コードも含めて継続して PASS させる
