## §1. ハイブリッド検索の仕様と設計

### 1.1 API と挙動

- 公開 API:
  - `POST /api/v1/search`
  - `POST /api/v1/feedback`
- 検索フロー:
  1. query + filters 受領
  2. lexical(ES) と semantic(ME5+VVS) 取得
  3. RRF 融合
  4. Feature View 経由特徴量取得
  5. KServe reranker で最終順位
  6. ranking/feedback を非同期記録

### 1.2 設計原則

- core は固定し、差分は adapter で吸収
- 6 軸 Port を維持（lexical / semantic / encoder / reranker / feature / log）
- Local は健全性確認、GCP は canonical 成立確認

### 1.3 reference

- 実案件参照構成: Elasticsearch + Redis 同義語 + ME5 + VVS + LightGBM

## 3. Cloud Composer の位置づけ (canonical 構成で本実装、Composer なし派生は引き算で派生)

**canonical 構成 で本線オーケストレーターとして本実装**し、Composer なし派生 相当環境はこの canonical 実装から引き算で派生させる。
`train/evaluate/register` は Vertex Pipelines に寄せ、Composer は上位 orchestration に専念する。
Vertex `PipelineJobSchedule` → **完全撤去**。

### 3.6 canonical / 引き算で派生する Composer なし派生 で禁止する状態

- Composer 本線 DAG を無効化して Cloud Scheduler 側を本線化すること
- Vertex `PipelineJobSchedule` を再導入して二重起動経路を作ること
- Feature View 経路を省略して serving 側の参照契約を崩すこと

## §2. Cloud Composer 本線 orchestration

### 2.1 役割分離

- Composer: 全体制御・運用オーケストレーション
- Vertex Pipelines: train/evaluate/register 実行

### 2.2 本線ポリシー

- 本線 retrain schedule は Composer のみ
- `PipelineJobSchedule` は併存禁止
- Cloud Scheduler / Eventarc / Cloud Functions は smoke/manual 用途に限定

### 2.3 3 DAG の責務

- `daily_feature_refresh`: 特徴量・index 更新
- `retrain_orchestration`: labeling〜retrain〜登録
- `monitoring_validation`: 評価〜gate〜反映

### 2.4 運用 surface

- `make composer-deploy-dags`
- `make ops-composer-trigger`
- `make ops-composer-list-runs`
- `make ops-composer-task-states`

## §3. Serving 層 (GKE + KServe)

### 3.1 構成

- `search-api`: GKE Deployment
- `property-encoder` / `property-reranker`: KServe InferenceService
- Gateway + IAP + NetworkPolicy で境界管理
- Model Registry alias を KServe `storageUri` へ反映
- 公開エンドポイント: `https://gcp-search-mlops-gke.dev` (Cloud Domains で取得、Cloud DNS public zone `gcp-search-mlops-gke-dev` で管理)。GKE Gateway (`gke-l7-global-external-managed`) が予約済グローバル外部 IP + Certificate Manager の Google-managed cert (DNS-01 authorization) で HTTPS 終端。`.dev` TLD は HSTS preload 強制。詳細は `infra/terraform/modules/dns/` / `runbook/05_運用.md`

### 3.2 課金の見方

- 常時系: Composer / GKE / Gateway / VVS / FOS / Elasticsearch
- 実行量系: Vertex Pipelines / Cloud Build / BigQuery / PubSub / Logging/Monitoring
- 詳細試算は `runbook/05_運用.md`

## §4. 検索ログ正解データパイプライン Port / Adapter

- `EventWriter` — canonical は **Pub/Sub** (`search-events` / `search-impressions` / `user-actions` の 3 topic → BigQuery Subscription で `mlops.{search_events,search_impressions,user_actions}` へ)。3 topic が未設定 (bootstrap 期) のときのみ `CloudLoggingEventWriter` にフォールバック
- `FeedbackRecorder` (Pub/Sub `search-feedback` topic → BQ Subscription) / `RankingLogPublisher` (Pub/Sub `ranking-log` topic → BQ Subscription)
- `EventRepository` / `LabelRepository` / `MetricsRepository` (BigQuery 読み)
- `TrainingDatasetRepository` (GCS)
- orchestration adapter は Composer/Vertex の上下関係に従う
