## §1. ハイブリッド検索の仕様と設計 (Phase 3-7 共通)

**canonical = Phase 7 [`docs/architecture/01_仕様と設計.md` §1](../../7/study-hybrid-search-gke/docs/architecture/01_仕様と設計.md)** (本ファイルでは要点のみ):

- **中核 5 要素 (不変)**: Meilisearch BM25 + multilingual-e5 + ベクトルストア (Phase 4 = BQ `VECTOR_SEARCH` / Phase 7 = Vertex AI Vector Search) + RRF + LightGBM LambdaRank
- **6 軸 Port/Adapter**: lexical retriever / semantic encoder / semantic vector store / reranker / feature fetcher / ranking log
- 中核置換は事前の明示合意必須

### Event schema 共通契約 (v3 設計改訂、2026-05-05)

`search_events` / `search_impressions` / `user_actions` の 3 テーブル + `action_type` enum 8 種 (`click` / `detail_view` / `favorite` / `request_button_click` / `request_complete` / `inquiry_complete` / `contract` / `bounce`) + 重み付き relevance label (`click`=1, `detail_view`=2, `favorite`=3, `request_button_click`=4, `request_complete`=5, `inquiry_complete`=7, `contract`=10, `no_action`=0, `bounce`=0/-1) は **Phase 3 PostgreSQL → Phase 4 BigQuery → Phase 7 Composer DAG で同型維持**。詳細は [`CLAUDE.md` 非負制約節](../../CLAUDE.md) と [`docs/将来展開-v3.md`](../将来展開-v3.md)。

### アプリ emit 5 種 vs synthetic 注入 4 種 (2026-05-05 補追)

- **アプリ emit 5 種** (Phase 3-7 全フェーズ共通の UI / Pydantic / EventWriter Port で実装): `click` / `detail_view` / `favorite` / `request_button_click` / `request_complete`
- **アプリ取得不可 4 種** (= synthetic 注入専用、UI / JS / Pydantic / EventWriter Port / `user_actions` INSERT 経路は **全フェーズで実装しない**): 長時間滞在 / `inquiry_complete` / `contract` / `bounce`。labeling_job が `definitions/labeling/synthetic_actions.yaml` に基づき `ranking_labels.label_source='synthetic_*'` で擬似正解データを書き込む
  - ※ **長時間滞在は `action_type` enum 値ではなく `action_value` 修飾子の概念** (`detail_view` の dwell time として `action_value` 列に入る予約)。enum 8 種にはカウントされない。詳細は Phase 3 [`docs/02_移行ロードマップ.md` §2.1](../../3/study-hybrid-search-local/docs/02_移行ロードマップ.md) (canonical)
- **Phase 3,4 アプリ差異の極小化** (canonical 設計原則): `app/` 配下 (UI / JS / Pydantic schema / Service / Port 定義) は Phase 3,4 で完全同一、adapter (DI 配線先) のみ差し替えで Phase 4 化が成立
- **`ml/labeling/policy.py` + `ml/labeling/synthetic_injector.py` + `definitions/labeling/synthetic_actions.yaml`** は Phase 3-7 で **不変の純粋ロジック / fixture** (psycopg / google.cloud import 禁止、AST 検出で死守)

## §7. 検索ログ正解データパイプライン + LightGBM 接続 (v3 設計改訂、2026-05-05)

> ⚠️ **canonical 死守ライン (重要)**: 下記表は **正解データを「収集する」経路の 3 段差**であり、
> **「LightGBM 学習側に届く」かどうかは別問題**。現状 (Phase 3 Wave 1-4 完了時点) では:
>
> - **Phase 3**: `pipeline/training_job/main.py` が `run(df=None)` を呼び `synthetic_ranking_frames(seed=42)`
>   で乱数学習 (= `ranking_labels` 未接続)。**Wave 7 で `ml/data/loaders/postgres_ranker_repository.py`
>   を新設し `training_job/main.py` から呼ぶ配線実装が必要** (Phase 3 [`docs/02_移行ロードマップ.md`
>   §0 不変ルール 0 + §5 Wave 7](../../3/study-hybrid-search-local/docs/02_移行ロードマップ.md))
> - **Phase 7**: 既存 `7/study-hybrid-search-gke/ml/data/loaders/ranker_repository.py` (BigQuery loader)
>   は実装済だが、`pipeline/training_job/main.py` が **これを呼んでいない** (= 配線忘れ、Phase 3 と
>   同様 synthetic only)。Composer DAG `retrain_orchestration` 駆動も同じく未接続
> - **Phase 4**: 上記 2 つの上に積む実装なので、**Phase 3 Wave 7 / Phase 7 配線実装が前提**
>
> いずれの Phase も **「ログ収集パイプライン」と「LightGBM 学習接続」は別工程** であることを
> 認識した上で表を読む。Wave 7 / 配線実装が完了するまで、表中の training dataset は LightGBM
> に届いていない (= モデル改善には繋がらない)。

| **Phase 3 (Local)** | PostgreSQL `search_events` / `search_impressions` / `user_actions` (ローカル最小契約) | 重み付き relevance ローカル labeling job (Python / SQL) → LightGBM training dataset (local CSV/Parquet) | 手動 (`make` ターゲット) | **⚠️ Wave 1-4 完了時点では未接続** (synthetic only)。Wave 7 で `postgres_ranker_repository.py` 新設 → trainer に df を渡す配線実装で接続 |

## §10. 不変ルール / 非負制約

### 全 Phase 共通

- 教材対象外技術は導入しない (本ファイル §11 / 親 [`README.md` §1](../../README.md))
- 設計思想 (Port/Adapter / 依存方向 / `core → ports ← adapters`) を破壊しない
- Phase 間のコード共有や広域リファクタは原則行わない

### Phase 3 / 4 / 7 (ハイブリッド検索系コード化対象)

- ハイブリッド検索中核 5 要素を維持 (詳細は Phase 7 docs/01 §1)
- 検索品質改善はこの基本構成を前提に行う
- 置換・削減・無効化は事前の明示合意を必要とする

### Phase 4 (GCP MLOps 土台 + 検索ログ正解データパイプライン = 独立コード)

- **Phase 7 完成版からの引き算ではなく、Phase 3 からの足し算で構築** (v3 設計改訂、2026-05-05)
- 主役は **検索アプリを改善し続けるための学習データ基盤**:
  - **基盤**: Cloud Run / Cloud Run Jobs / BigQuery / GCS / Secret Manager / Cloud Logging / Artifact Registry / Cloud Build / Terraform / WIF / IAM
  - **行動ログパイプライン**: Cloud Run 構造化ログ → Cloud Logging → GCS raw event bucket → BigQuery `raw_events` / `curated` → labeling SQL → BigQuery `ranking_labels` / `training_dataset` → BigQuery `evaluation_metrics` (NDCG@10 / Recall@K / CTR / CVR)
  - **再学習 trigger**: Cloud Scheduler + Eventarc + Cloud Function による軽量 orchestration → Cloud Run Job retrain → GCS model artifact 保存
  - **ベクトル検索**: BigQuery `VECTOR_SEARCH` (GCP マネージドサービス基礎習得の範囲、Vertex Vector Search への置換は Phase 7 で実施)
- **Phase 4 の到達点**: BigQuery 上で NDCG@10 / Recall@K / CTR / CVR を計算でき、再学習候補モデルを GCS に作れること。Vertex Model Registry 登録は Phase 7 側に寄せる
- **Vertex AI Pipelines / Feature Store / Vector Search / Vertex Model Registry / Cloud Composer / Dataflow / GKE / KServe / PMLE 追加技術は扱わない** (Phase 7 完成版に集約、Phase 5 / 6 で分解説明)

### Phase 5 / 6 (論理 Phase = コード保守なし)

- 個別コードを持たない。Phase 7 完成版コードを基準にして技術境界を資料化する
- 各 Phase スライド・ドキュメントでは Phase 7 配下の参照先を必ず明示する

### Phase 7 (到達ゴール = canonical 起点)

- Phase 5 / 6 の技術要素も Phase 7 配下に集約
- Cloud Composer 本線 + Vertex AI Pipelines + Feature Store + Vertex Vector Search + Model Registry + BigQuery + Meilisearch + GKE + KServe + PMLE 4 技術を本 phase で本実装
- ハイブリッド検索中核コードの挙動は絶対に変えない
- default feature flag では Phase 5 相当の挙動を維持 (新技術は opt-in)
- `make check` / parity invariant / Port/Adapter 境界検知 / WIF は追加コードも含めて継続して PASS させる
