→コーディングは済んだ。

その実装と検証が済めば、Phase07 にも、正解データ、データパイプライン、GBM に正解データを作用させる仕組みを反映させる。
→Phase07でのローカル動作が今日の目標

- Phase 3:
  - ユーザー向け検索画面
  - 物件詳細ページ
  - 行動ログ収集
  - 正解データ作成の最小導線
  - 管理画面は作らない

- Phase 4:
  - GCS / BigQuery / metrics / training dataset 化
  - 管理画面は作らない

> 目的:
> 現行の不動産ハイブリッド検索アプリを、単発検索デモではなく
> **行動ログから正解データを作り、継続的にランキング改善できる教材**
> として再整理する。

---

## 1. 背景

現状のコードベースは、ローカル・GCP の両方で検索アプリとしては成立しているが、
検索品質を改善し続けるための **正解データ経路** が弱い。

不足しているのは次の流れである。

```text
検索
→ 表示
→ 行動ログ
→ ラベル化
→ 学習データ化
→ 再学習
→ 評価
→ 再配備判断
```

この不足を埋めるとき、題材は引き続き **不動産検索** とし、Phase 構成はできるだけ維持する。

---

## 2. 前提方針

### 2.1 変えないこと

- Phase 1 / 2 / 3 / 4 / 7 をコード化対象とする大枠
- Phase 5 / 6 を論理 Phase として扱う整理
- 不動産ハイブリッド検索という題材
- Phase 7 を canonical とする設計方針

### 2.2 変えること

- Phase 3 に **ローカル最小版の行動ログとラベル化** を入れる
- Phase 4 を単なる GCP 化ではなく
  **検索ログ正解データパイプラインを持つ MLOps 土台**
  として明確化する
- Phase 7 ではその完成版として
  Composer / Vertex / GKE / KServe まで接続する

---

## 3. 結論

**新しい Phase を追加する必要は薄い。**

最適な整理は、既存の 7 Phase を維持したまま、
**Phase 3 / 4 / 7 に「行動ログ → 正解データ → 継続改善」の段差を埋め込むこと**である。

推奨する役割分担は次の通り。

| Phase | 役割 | 正解データ / 継続改善の位置づけ | コード化 |
|---|---|---|---|
| 1 | ML 基礎 | 正解が明確な教師あり学習 | あり |
| 2 | App / Pipeline / Port-Adapter | API・batch・train の責務分離 | あり |
| 3 | Local ハイブリッド検索 | ローカルで最小行動ログ収集、簡易ラベル化、再学習 | あり |
| 4 | GCP MLOps 土台 + 検索ログデータ基盤 | GCS / BigQuery / Cloud Run Jobs で正解データ整備 | あり |
| 5 | Vertex AI MLOps 境界 | Phase 7 の Vertex 系を分解して学ぶ | なし |
| 6 | PMLE / Composer 境界 | Phase 7 の Composer / Dataflow / Monitoring を分解して学ぶ | なし |
| 7 | 教材コード完成版 | 継続改善サイクルの本実装 | あり |

Phase 4 の名称も、次のように寄せるのが自然。

```text
Phase 4: GCP MLOps の土台 + 検索ログ正解データパイプライン
```

UI 方針も固定する。

- Phase 3 はユーザー向け検索画面と物件詳細ページまで
- Phase 4 は管理画面を作らない
- Phase 7 だけ `/admin/mlops` の 1 ページを追加する

## 4. 収集すべき行動ログ

全行動を実装する必要はない。  
重要で、かつ現行コードから現実的に実装できるものに絞る。

| 行動 | 強さ | 扱い |
|---|---:|---|
| 検索結果に表示 | なし | impression |
| 物件クリック | 弱い正例 | weak positive |
| 詳細ページ閲覧 | 中程度の正例 | positive |
| 長時間滞在 | 中程度の正例 | positive |
| お気に入り | 強い正例 | strong positive |
| 資料請求ボタンクリック | 強い正例 | strong positive |
| 資料請求完了 | かなり強い正例 | very strong positive |
| 問い合わせ完了 | かなり強い正例 | very strong positive |
| 成約 | 最強の正例 | final conversion |
| 表示されたがクリックなし | 弱い負例 | weak negative |
| クリック後すぐ離脱 | 弱い負例 | weak negative |

この中で、Phase 3 の最小実装として特に重要なのは次。

- impression
- click
- detail_view
- favorite
- request_button_click
- request_complete

そのため、**物件詳細ページは必須**とする。

## 6. ラベル作成の基本方針

検索では正解データが最初から存在しないため、
行動ログから **弱教師ありラベル** を作る。

最初は単純な重み付き relevance label で十分。

```text
click: 1
detail_view: 2
favorite: 3
request_button_click: 4
request_complete: 5
inquiry_complete: 7
contract: 10
no_action_impression: 0
bounce_after_click: 0 or -1
```

学習データの最終形は LambdaRank 前提で次のようにする。

```text
query_id, search_id, property_id, relevance_label, features...
```

## 7. Phase 3 に入れるべきもの

Phase 3 は単なるローカル検索デモではなく、
**ローカルで正解データの最小サイクルを体験する Phase** にする。

入れるべき要素:

- PostgreSQL に `search_events` / `search_impressions` / `user_actions` / `ranking_labels`
- 物件詳細ページ
- `/feedback` だけでなく詳細画面由来の行動ログ
- labeling job
- training dataset builder
- LightGBM reranker 再学習
- GBM に正解データを実際に作用させる学習経路
- ローカルでの NDCG / MAP / Recall 確認
- Redis の実利用

画面は次に限定する。

- ユーザー向け検索画面
- 物件詳細ページ
- 正解データ作成の最小導線

**管理画面は作らない。**

Redis は「入れたことにする」状態を避ける。最低限、次のどれかではなく、
**少なくとも検索キャッシュは必須で動作確認対象**にする。

- query / result cache
- embedding cache
- rerank feature cache

受け入れ条件の例:

- cache miss では本体検索が走る
- cache hit では不要な adapter 呼び出しが抑制される
- 同一 query + filters で key が安定する
- TTL が設定される

## 10. Port / Adapter 設計方針

Phase ごとに実装は別でも、アプリから見える呼び口はそろえる。

例:

```python
event_writer.emit_search_event(...)
event_writer.emit_impression(...)
event_writer.emit_user_action(...)
```

保存先の違いは adapter 側で吸収する。

- Phase 3: PostgreSQL
- Phase 4: Cloud Logging / GCS / BigQuery
- Phase 7: BigQuery / Composer / Vertex / GKE / KServe 連携

重要なのは、**アプリ本体が保存先を知らないこと**である。

## 12. 最終判断

このカリキュラムは、次の軸に整理すると最も一貫する。

```text
Phase 1:
正解が明確な ML 基礎

Phase 2:
App / Pipeline / Port-Adapter

Phase 3:
検索アプリ + ローカル行動ログ + 弱教師ラベル作成

Phase 4:
Cloud Run + GCS + BigQuery による検索ログ正解データパイプライン

Phase 5:
Vertex AI MLOps を Phase 7 から分解して理解

Phase 6:
PMLE / Composer を Phase 7 から分解して理解

Phase 7:
GKE + KServe + Composer + Vertex による完成版 MLOps
```

要点は 1 つだけである。

**Phase 4 を「Cloud 化」ではなく「検索改善データ基盤の Cloud 化」として再定義する。**

これにより、単なる GCP 学習ではなく、
**行動ログから正解データを作り、ランキングモデルを継続改善する教材**
として全体がつながる。
