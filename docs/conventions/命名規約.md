# Conventions

本リポジトリのフォルダ名・ファイル名・役割の共通規約。  
狙いは、**同じ概念は同じ名前で置く**こと。

## 基本方針

- 機能別の名前を優先し、レイヤー別の名前は内側に閉じ込める

## ルート直下の標準形

```text
.
├── README.md
├── CLAUDE.md
├── Makefile
├── pyproject.toml
├── app/
├── ml/
├── pipeline/
├── scripts/
├── infra/
├── env/
├── docs/
├── tests/
├── tools/
└── logs/
```

## `ml/` 規約

`ml/` は機能別を正とする。

```text
ml/
├── common/
├── data/
├── training/
├── evaluation/
├── registry/
├── serving/
├── streaming/
└── experiment/
```

ルール:

- `adapters` `ports` `core` を `ml/` 直下に置かない
- 必要なら `ml/training/adapters/` のように機能ディレクトリの下へ置く

## `pipeline/` 規約

`pipeline/` は `<verb>_job` を正とする。

```text
pipeline/
├── data_job/
├── training_job/
├── evaluation_job/
├── batch_serving_job/
└── workflow/
```

ルール:

- `train_job` ではなく `training_job`
- `predict_job` ではなく `batch_serving_job`
- `seed_job` は `data_job` に寄せる
- レイヤー構造は `pipeline/<job>/` の内側で表現する

## `scripts/` 規約

`scripts/` は公開 API と内部実装を分ける。

```text
scripts/
├── _common.py
├── setup/
├── deploy/
├── ops/
├── ci/
├── sql/
└── bqml/
```

ルール:

- `Make target = ユーザー向け公開 API`
- `scripts/setup` `scripts/deploy` `scripts/ops` = canonical
- `core.py` は新規採用しない。共通ユーティリティは `_common.py` に寄せる

## `docs/` 規約

```text
docs/
├── architecture/
│   ├── 01_仕様と設計.md
│   └── 03_実装カタログ.md
├── tasks/
│   ├── TASKS.md
│   └── TASKS_ROADMAP.md
├── runbook/
│   ├── 04_検証.md
│   └── 05_運用.md
├── conventions/
└── decisions/
```

ルール:

- `architecture/01` = 仕様
- `architecture/03` = 実装マップ
- `tasks/TASKS.md` = current sprint
- `tasks/TASKS_ROADMAP.md` = 長期 backlog
- `runbook/04` = 検証、`runbook/05` = 運用

## `tests/` 規約

```text
tests/
├── unit/
├── integration/
└── e2e/
```

ルール:

- 基本は `tests/` 集約
- package 直下の `app/tests` などは例外扱い

## 非推奨

- `core.py` を新規で増やすこと
- `ml/` や `pipeline/` の直下で概念名を変えること

## 優先順位

1. `CLAUDE.md`
2. この `命名規約.md` (同 dir)
3. 同階層の [`スクリプト規約.md`](スクリプト規約.md) / [`Makefile規約.md`](Makefile規約.md) / [`フォルダ-ファイル.md`](フォルダ-ファイル.md) / [`Docker配置規約.md`](Docker配置規約.md)
4. `README.md` と `docs/`
