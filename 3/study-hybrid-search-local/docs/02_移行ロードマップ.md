## 2. Wave 5-8 (本ロードマップの中核、2026-05-05 着手 / v3 設計改訂反映)

### 2.0 Wave 5-8 全体像 (将来展開-v3アプリ改修.md 反映)

将来展開資料の **継続改善 MLOps サイクル** (`行動ログ → 正解データ → 再学習 → 評価 → deployment gate`) を Phase 3 ローカル最小構成で一巡させる。

```text
[現行 Wave 1-4]
  /search → ranking_log (impression full pool)
  /feedback → feedback_events (click / favorite / inquiry の 3 種のみ)

[Wave 5-8 で追加するもの]
  /search → 加えて search_events + search_impressions (新 3 テーブルへ並行 publish)
  /ui/property/{id}                         ← 物件詳細ページ (新規)
  /feedback (拡張) → user_actions (8 種 enum で拡張)
    + click / detail_view / favorite / request_button_click / request_complete + 派生 impression / no_action
  pipeline/labeling_job (新規)              ← 重み付き relevance label
  pipeline/training_dataset_job (新規)      ← LightGBM LambdaRank 用 CSV/Parquet 出力
  ml/training/trainer (改修)                ← synthetic fallback → ranking_labels 由来へ切替
  Make: label / build-training-dataset      ← 新ターゲット
  evaluation_job (改修)                     ← labeled holdout で NDCG@10 + CTR / CVR 評価
```

### 2.1 11 行動の篩い分け (User 指示「現行コードから実装が現実的なもの」に限定)

User 提示の 11 行動を Phase 3 scope と Phase 4 scope に **decisive に分類** する (canonical 必須項目を「別 sprint 候補」で逃さない)。

| # | 行動 | 強さ | Phase 3 (Wave 5-8) | Phase 3 で扱わない理由 (該当する場合) | 出処 |
|---|---|---|---|---|---|
| 1 | 検索結果に表示 (impression) | なし | ✅ 実装 (派生) | — | 既存 `ranking_log` から `search_impressions` へ並行 publish |
| 2 | 物件クリック (click) | 弱い正例 | ✅ 実装 (拡張) | — | 既存 `feedback_events.action='click'` を `user_actions.action_type='click'` に汎化。`_search_results.html` のカードに `<a href="/ui/property/{id}">` リンク追加 + JS で sendBeacon |
| 3 | 詳細ページ閲覧 (detail_view) | 中程度の正例 | ✅ **新規** | — | `/ui/property/{id}` 表示時に JS から `POST /feedback` で発火 |
| 4 | 長時間滞在 | 中程度の正例 | 🟡 **実装対象外** (synthetic 注入) | アプリからログ取得しない (User 指示 2026-05-05)。dwell time 計測の UI / JS / adapter は実装せず、Wave 6 labeling_job で `ranking_labels` に synthetic 注入で擬似正解データを作る | Phase 3-7 全て synthetic only。`action_type` enum に独立値は持たない (元々持っていない、`detail_view` の `action_value` 修飾子だった概念) |
| 5 | お気に入り (favorite) | 強い正例 | ✅ 実装 (拡張) | — | 既存 `feedback_events.action='favorite'` を汎化、詳細ページの「お気に入り」button を中核 UI 化 |
| 6 | 資料請求ボタンクリック (request_button_click) | 強い正例 | ✅ **新規** | — | 詳細ページ「資料請求」button click |
| 7 | 資料請求完了 (request_complete) | かなり強い正例 | ✅ **新規** | — | 詳細ページ簡易フォーム (name / email / message) submit (送信先なし、ローカル DB 記録のみ) |
| 8 | 問い合わせ完了 (inquiry_complete) | かなり強い正例 | 🟡 **実装対象外** (synthetic 注入) | アプリからログ取得しない (User 指示 2026-05-05)。資料請求とほぼ重複、教材簡素化のため request_complete に一本化。Wave 6 labeling_job で synthetic 注入 | Phase 3-7 全て synthetic only。`action_type` enum には予約 (Phase 4 接続契約のため) |
| 9 | 成約 (contract) | 最強の正例 | 🟡 **実装対象外** (synthetic 注入) | UI 上の操作で発生せず、CRM 連携が必要。Wave 6 labeling_job で synthetic 注入 | Phase 3-7 全て synthetic only。`action_type` enum には予約 |
| 10 | 表示されたがクリックなし (no_action) | 弱い負例 | ✅ **派生 SQL のみ** | — | `search_impressions` × `user_actions` の差分で labeling job が SQL 派生 |
| 11 | クリック後すぐ離脱 (bounce) | 弱い負例 | 🟡 **実装対象外** (synthetic 注入) | アプリからログ取得しない (User 指示 2026-05-05)。dwell time 計測の UI / JS / adapter は実装せず、Wave 6 labeling_job で synthetic 注入 | Phase 3-7 全て synthetic only。`action_type` enum には予約 |

**結論**: Phase 3 の **アプリから実取得する行動は 5 種** (click / detail_view / favorite / request_button_click / request_complete) + **派生 2 種** (impression は `ranking_log` から並行 publish、no_action は SQL 派生)。

**実装対象外 4 種の扱い** (User 指示 2026-05-05): 長時間滞在 / inquiry_complete / contract / bounce は **アプリからログ取得せず、Wave 6 labeling_job で `ranking_labels` に synthetic 注入** で擬似正解データを作る (詳細は §4.7)。dwell tracking / 問い合わせフォーム / CRM 連携は **Phase 3-7 全フェーズで実装しない** (= 「アプリからログとれない」前提が canonical、Phase 4 への先送りでもない)。

**`action_type` enum 設計**: Phase 4 接続契約のため **8 種すべて予約** (`click` / `detail_view` / `favorite` / `request_button_click` / `request_complete` / `inquiry_complete` / `contract` / `bounce`)。アプリ emit は 5 種、`user_actions` テーブルへの insert は 5 種のみ。残り 3 種 (`inquiry_complete` / `contract` / `bounce`) は **Wave 6 labeling_job が `ranking_labels.label_source` 列にて synthetic 注入の根拠としてのみ使う** (= `user_actions` には登場しないが enum 定義は同型維持)。長時間滞在は元々 `action_type` enum 値ではなく `action_value` 修飾子だった概念のため、enum 変更なし。

## 3. Wave 5: Event schema 標準化 + 物件詳細ページ (UI 改修)

### 3.1 目的

将来展開-v3アプリ改修.md の **継続改善サイクルの土台** を Phase 3 ローカル PostgreSQL 上で確立する。検索結果一覧 → **物件詳細ページ** → 資料請求ボタン → 資料請求フォーム送信 という 1 本の正解データ取得導線を作り、3 テーブル契約 (`search_events` / `search_impressions` / `user_actions`) に永続化する。

### 3.2 受け入れ条件 (Wave 5 完了の判定)

1. ✅ `definitions/postgres/migrations/0002_event_schema.sql` で 3 新テーブル + `ranking_labels` テーブル + `action_type_enum` を作成し `make seed` 実行で migration 完走
2. ✅ `/ui/property/{property_id}` ページが 200 を返し、物件マスタ情報 (title / description / city / ward / layout / rent / walk_min / area_m2 / age_years / pet_ok) を表示する
3. ✅ 詳細ページに「お気に入り」ボタン + 「資料請求」ボタン + 簡易フォーム (name / email / message) を配置
4. ✅ JS (詳細ページロード時 / button click / form submit 時) から `POST /feedback` を発火し、`user_actions` に `action_type` ∈ {`detail_view`, `favorite`, `request_button_click`, `request_complete`} で永続化される
5. ✅ `_search_results.html` のカードに `<a href="/ui/property/{id}">` リンクを追加し、リンク click 時に `user_actions.action_type='click'` を JS から発火
6. ✅ `/search` 実行時に `search_events` 1 行 + `search_impressions` N 行 (final pool 全件) が新規 publish される (既存 `ranking_log` への publish は並行維持)
7. ✅ `make verify-pipeline` で integration E2E が PASS (新規 case: 物件詳細ページ 200 / `user_actions` INSERT 確認 / `search_events` + `search_impressions` 永続化)
8. ✅ `make check-layers` で AST 境界 0 違反 (新 Port / 新 adapter / 新 Router を追加した後も)

### 3.3 DDL 変更 (`definitions/postgres/migrations/0002_event_schema.sql` 新規)

```sql
-- 0002_event_schema.sql (Wave 5 で新規追加、0001_init.sql は不変)

-- action_type enum (Phase 4 接続契約のため 8 種すべて予約)
-- アプリ emit は 5 種のみ (User 指示 2026-05-05、§2.1 参照)。残り 3 種は Wave 6 synthetic 注入専用
-- (詳細は §4.7、ranking_labels.label_source へ TEXT として書き込む。user_actions テーブルへの INSERT 経路はない)
CREATE TYPE action_type_enum AS ENUM (
    -- アプリ emit (Phase 3-7 全フェーズ共通、UI / Adapter / Pydantic で実装):
    'click',                    -- 検索結果カードのリンク click (Phase 3 UI 実装)
    'detail_view',              -- 物件詳細ページ表示 (Phase 3 UI 実装)
    'favorite',                 -- お気に入り登録 (Phase 3 UI 実装)
    'request_button_click',     -- 詳細ページの「資料請求」button click (Phase 3 UI 実装)
    'request_complete',         -- 簡易フォーム submit 完了 (Phase 3 UI 実装)
    -- 実装対象外 (Phase 3-7 全フェーズで synthetic 注入のみ、user_actions への INSERT なし):
    'inquiry_complete',         -- 問い合わせ完了 — アプリ取得不可 (UI 実装なし、Phase 4 でも tracking しない)
    'contract',                 -- 成約 — CRM 連携が必要、教材スコープ外
    'bounce'                    -- クリック後すぐ離脱 — dwell time 計測なし (Phase 3,4 でアプリ差異を作らない方針)
);

-- search_events: /search 1 リクエストにつき 1 行
CREATE TABLE IF NOT EXISTS search_events (
    event_id           BIGSERIAL PRIMARY KEY,
    search_id          TEXT NOT NULL UNIQUE,             -- request_id を流用
    user_id            TEXT,                              -- Phase 3 では NULL (将来: ブラウザセッションから生成)
    session_id         TEXT,                              -- Phase 3 では NULL
    query              TEXT NOT NULL,
    filters_json       JSONB NOT NULL DEFAULT '{}'::jsonb,
    timestamp          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    app_version        TEXT,                              -- search-api version (env から)
    model_version      TEXT                               -- reranker model_path
);
CREATE INDEX IF NOT EXISTS search_events_timestamp_idx ON search_events (timestamp);

-- search_impressions: /search の final pool 1 候補につき 1 行
CREATE TABLE IF NOT EXISTS search_impressions (
    event_id           BIGSERIAL PRIMARY KEY,
    search_id          TEXT NOT NULL,                     -- search_events.search_id への外部キー
    property_id        TEXT NOT NULL,
    rank               INTEGER NOT NULL,                  -- final_rank (1-based)
    lexical_rank_orig  INTEGER,                           -- 既存 ranking_log.lexical_rank (FEATURE_COLS_RANKER 互換用)
    semantic_rank_orig INTEGER,                           -- 既存 ranking_log.semantic_rank (同上)
    lexical_score      REAL,                              -- BM25 score 正規化値 (Phase 4 で BQ に同型移植)
    vector_score       REAL,                              -- 既存 ranking_log.me5_score
    rrf_score          REAL,                              -- RRF 合成 score (新規取得)
    rerank_score       REAL,                              -- 既存 ranking_log.score (LightGBM 出力)
    timestamp          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS search_impressions_search_idx ON search_impressions (search_id);
CREATE INDEX IF NOT EXISTS search_impressions_property_idx ON search_impressions (property_id);

-- user_actions: 行動ログ (impression は search_impressions に既にあるので含めない)
CREATE TABLE IF NOT EXISTS user_actions (
    event_id           BIGSERIAL PRIMARY KEY,
    search_id          TEXT NOT NULL,                     -- search_events.search_id 由来
    property_id        TEXT NOT NULL,
    action_type        action_type_enum NOT NULL,
    action_value       REAL,                              -- 拡張用 (Phase 4 dwell time 等。Phase 3 UI からは NULL)
    timestamp          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (search_id, property_id, action_type)          -- 冪等性 (二重発火防止)
);
CREATE INDEX IF NOT EXISTS user_actions_search_idx ON user_actions (search_id);
CREATE INDEX IF NOT EXISTS user_actions_action_type_idx ON user_actions (action_type);

-- ranking_labels: labeling job (Wave 6) で書き込む。LightGBM LambdaRank 学習用
CREATE TABLE IF NOT EXISTS ranking_labels (
    search_id          TEXT NOT NULL,
    property_id        TEXT NOT NULL,
    relevance_label    REAL NOT NULL,                     -- 重み付き合算結果 (0 / 1 / 2 / 3 / 4 / 5 / 7 / 10 等)
    label_source       TEXT NOT NULL,                     -- 'no_action' / 'click' / 'detail_view' / ... (label 計算根拠の最強アクション)
    created_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (search_id, property_id)
);
CREATE INDEX IF NOT EXISTS ranking_labels_search_idx ON ranking_labels (search_id);

-- 既存 ranking_log / feedback_events は削除しない (back-compat、Wave 5 では並行 publish)
```

**設計判断**:
- `search_id` = `request_id` (流用、別 ID 体系を作らない)
- 既存 `ranking_log` (10 列) と新 `search_impressions` は **重複保持**。Wave 5 では並行 publish (back-compat)、`ranking_log` のレガシー化は Wave 8 後に判断
- 既存 `feedback_events` (3 種 enum CHECK 制約) は残す。新 `user_actions` (8 種 ENUM 型) と並行 publish
- `action_type_enum` を PostgreSQL ENUM 型で作成 (`CHECK` 制約だと Phase 4 BigQuery への型同期がしにくい、ENUM の方が schema 同期が綺麗)
- `bounce` の `action_value` には dwell ms を入れる予約 (Phase 3 では発火しない)
- `search_impressions.lexical_rank_orig` / `semantic_rank_orig` は `FEATURE_COLS_RANKER` の既存 10 列との parity 維持用 (Wave 7 で training dataset を組む時に使用)

### 4.1 目的

5. ✅ ユニットテスト `tests/unit/ml/test_labeling_policy.py` で重み付き合算ロジックが PASS (各 action_type 単独 + 複合 + bounce + no_action)

### 4.3 重み付き relevance label 計算ロジック (将来展開-v3 と同期)

```python
# ml/labeling/policy.py (新規)
ACTION_WEIGHTS: dict[str, int] = {
    "click": 1,
    "detail_view": 2,
    "favorite": 3,
    "request_button_click": 4,
    "request_complete": 5,
    "inquiry_complete": 7,
    "contract": 10,
    # bounce / no_action は別ロジック (下記 compute_label 内)
}

def compute_label(
    *,
    actions_for_property: list[str],   # 同 search_id × property_id に対する全 action_type
    impression_present: bool,           # search_impressions に該当行あり
) -> tuple[float, str]:
    """重み付き relevance label を返す。

    Returns:
        (relevance_label, label_source)
    """
    if not impression_present:
        # impression が無い ⇒ そもそも検索結果に出ていない (例外的、無視)
        return (0.0, "no_impression")
    if not actions_for_property:
        # impression あり、action なし = no_action (弱い負例)
        return (0.0, "no_action")
    if "bounce" in actions_for_property:
        # クリック後すぐ離脱 (Phase 3 では発火しないが、Phase 4 で発火する場合に備える)
        return (-1.0, "bounce")
    # 最強の action を採用 (将来展開-v3.md L1004-1014「複合ラベル」と整合)
    weights = [ACTION_WEIGHTS[a] for a in actions_for_property if a in ACTION_WEIGHTS]
    if not weights:
        return (0.0, "no_action")
    max_weight = max(weights)
    strongest_action = max(
        actions_for_property,
        key=lambda a: ACTION_WEIGHTS.get(a, 0),
    )
    return (float(max_weight), strongest_action)
```

**設計判断**:
- 「単純合算」ではなく「最強の action の重み」を採用 (将来展開-v3 §「複合ラベル」と整合、教材として解釈しやすい)
- `bounce` は Phase 3 では発火しないが、Phase 4 で `action_value=dwell_ms` 付きで発火する想定があるため policy.py に予約
- `no_action` は派生 (impression あり × action なし)、`ranking_labels` に label=0 で UPSERT
- impression が無い (`no_impression`) は labeling 対象外 (そもそも検索結果に出ていない property、学習データに含めない)
- **policy.py は SDK / DB import 禁止** (純粋関数、`scripts/ci/layers.py` で `psycopg` / `google.cloud` / `redis` / `lightgbm` を禁止) → Phase 4 でも不変

### 4.4 labeling_job 実装 (`pipeline/data_job/components/sync_synonyms.py` のパターン踏襲)

```python
# pipeline/labeling_job/main.py (新規)
"""Labeling job for Phase 3 ranking_labels.

Reads search_impressions × user_actions from PostgreSQL,
applies ml.labeling.policy.compute_label, and UPSERTs ranking_labels.

Idempotent: re-running on the same data produces identical ranking_labels.
"""

def run(*, dsn: str, since: datetime | None = None) -> int:
    event_repo = PostgresEventRepository(dsn=dsn)
    label_repo = PostgresLabelRepository(dsn=dsn)
    impressions = event_repo.read_impressions(since=since)
    actions = event_repo.read_user_actions(since=since)
    grouped: dict[tuple[str, str], dict] = ...  # search_id × property_id でグルーピング
    labels: list[RankingLabel] = []
    for (search_id, property_id), data in grouped.items():
        relevance, source = compute_label(
            actions_for_property=data["actions"],
            impression_present=data["impression_present"],
        )
        labels.append(RankingLabel(
            search_id=search_id,
            property_id=property_id,
            relevance_label=relevance,
            label_source=source,
        ))
    label_repo.write_ranking_labels(labels)
    return len(labels)

def main(argv: list[str] | None = None) -> int: ...  # CLI entry point
```

### 4.7 Synthetic 注入 (アプリから取得できない 4 種の擬似正解データ作成、User 指示 2026-05-05)

**目的**: `inquiry_complete` / `contract` / `bounce` / 長時間滞在 はアプリから実取得しない (§2.1)。これらに相当する正解データは labeling_job で **synthetic 注入** によって `ranking_labels` に直接書き込み、LightGBM 学習データの強い正例 / 強い負例の variance を確保する。

**設計原則**:
- アプリ側 (UI / JS / Pydantic / EventWriter Port / `user_actions` テーブル) は触らない (= Phase 3,4 アプリ差異の極小化)
- 注入は labeling_job の **stage 2** として `compute_label` 呼び出し後に追加実行 (実取得 → label 計算 → synthetic 注入 → UPSERT の順)
- 注入元は YAML fixture (`definitions/labeling/synthetic_actions.yaml`) または既存 `feature_mart_property_features_daily.inquiry_rate` を確率的に解釈
- 注入された行は `ranking_labels.label_source` に `synthetic_inquiry_complete` / `synthetic_contract` / `synthetic_bounce` / `synthetic_long_stay` を記録 (実取得との区別、後で除外学習や A/B 比較が可能)
- 同 `(search_id, property_id)` で実取得 label が既にある場合は注入しない (実データ優先、PRIMARY KEY 衝突回避)

**`definitions/labeling/synthetic_actions.yaml` 例**:

### 5.5 LocalTrainingDatasetRepository (Phase 4 への足し算地点)

```python
# app/services/adapters/local_training_dataset_repository.py
class LocalTrainingDatasetRepository(TrainingDatasetRepository):
    def __init__(self, *, root: Path) -> None:
        self._root = root
        self._root.mkdir(parents=True, exist_ok=True)

    def write_training_dataset(self, *, run_id: str, df: pd.DataFrame) -> Path:
        run_dir = self._root / run_id
        run_dir.mkdir(parents=True, exist_ok=True)
        path = run_dir / "training.parquet"
        df.to_parquet(path, index=False)
        return path

    def read_training_dataset(self, *, run_id: str) -> pd.DataFrame:
        path = self._root / run_id / "training.parquet"
        return pd.read_parquet(path)
```

Phase 4 で `gcs_training_dataset_repository` に差し替えれば GCS object へ書き出しに変わる (Port 不変、adapter 差し替えのみ)。
